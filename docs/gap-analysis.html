先说结论

v7-cms 是第 3 类——Git / Markdown 型 CMS，而且在这一类里它的定位是清楚的: 给静态站点一个不糟蹋你文件的编辑器。它已经解决了 Decap、Keystatic、Sveltia 都没解决的那个问题—— 嵌套对象字段（相册里每张照片带可选的相机参数子对象）。

下面这份清单里的绝大多数条目，不是"还没做"，而是"不该做"——做了就会变成第 1、2、4 类里更差的那个。 真正值得投入的只有三条，在第 3 节。

2 · 对照其他三类：不做的部分

不做

插件市场与主题市场（WordPress / Drupal）

理由：插件生态是网络效应，不是功能。WordPress 的护城河是两万个插件和二十年社区，代码量反而次要。而一个能装任意第三方插件的 CMS，必须放弃"绝不改动未编辑内容"这个保证——插件要能改渲染、改存储、改表单。那正好是 v7-cms 唯一的核心资产。

替代：已经有的 registerPlugin()（字段类型 / 预览渲染器 / 主题令牌）。消费方注册东西，而不是插进别人的代码。这是对的规模。

不做

复杂权限与角色（Drupal / Umbraco）

理由：权限模型属于后端。Git 已经有一套现成的、所有人都懂的权限系统——仓库写权限。/api/auth 现在就是按 GitHub 的 permissions.push 判定的。再叠一层自己的角色，等于要维护用户表、会话、审计日志，而 v7-cms 是静态产物，一个字节的服务端状态都没有。

能做的：GitHub 的团队权限、分支保护规则、CODEOWNERS——都用仓库自己的机制，不重复实现。

不做

GraphQL / REST API、内容联邦（Strapi / Contentful / Sanity）

理由：这一类的前提是内容存在数据库里、由服务端按需投递。v7-cms 的内容是仓库里的文件，消费方是静态构建器。"把内容变成 API"在这个架构里是反向的——文件本身就是 API，git clone 就是最通用的接口。

真实的差距：Sanity 的 GROQ 之所以强，是因为它能对结构化内容做任意查询。静态站点不需要这个——需要查询的是构建期，而构建期有完整语言可用。

不做

拖拽页面构建器（Storyblok）

理由：可视化拖拽生成的是布局，不是内容。它要求页面结构可被 CMS 理解并可写回——对 Markdown / MDX 来说，这意味着把作者的源码拆成组件树再拼回去。这与"字节保真"直接冲突，也会让 MDX 里手写的 JSX 无法存活。

注意：清单里 TinaCMS 的"可视化内联编辑"是另一件事——它不是拖拽布局，而是在渲染页面上直接改已有字段。这个见第 3 节，是值得做的。

不做

会员 / 付费订阅 / 邮件通讯（Ghost）

理由：这是商业模式，不是 CMS 功能。它需要支付网关、订阅状态机、邮件投递、退订合规（CAN-SPAM / GDPR）。Ghost 之所以做得好，是因为它是一家公司在运营这套服务，而不是因为它代码里有个字段。

能做的：静态站点接第三方（Buttondown、Stripe Payment Links）比自建划算得多。

不做

全球 CDN 分发、内容联邦、多地域（Contentful / Hygraph）

理由：静态站点的 CDN 由托管方提供（这个博客就是 Cloudflare 的全球网络）。CMS 不需要知道边缘节点在哪。

3 · 值得做的三条

按"对当前用户的真实收益 ÷ 工程量"排序。前两条我已经做完并发布了，第三条是真正的下一步。

  1. 账号可见性与退出登录 —— 已完成

    编辑器持有一个能写仓库的凭据，却既不显示当前身份，也没有退出口。tokenStore.clear() 存在但无人调用。现在侧边栏底部显示登录名、会话来源（GitHub 登录 / 访问令牌），以及需要二次确认的退出按钮。没有账号的后端（本地文件夹）不显示退出，避免给一个点了没反应的按钮。

    v7-cms v0.0.0-alpha.5

  2. 界面的完整翻译 —— 已完成

    locale 此前被接受、校验，然后从未被读取——唯一的引用是一句两个分支返回同一字符串的死三元表达式。zh-CN 的站点得到英文界面，而且没有任何测试失败。现在有 en / zh-CN 两本词典，约 80 条文案。Dictionary 类型从英文键映射而来，所以漏译是编译错误而不是空白标签。

    v7-cms v0.0.0-alpha.2

  3. 可视化内联编辑 —— 真正的下一步

    这是清单里唯一与 v7-cms 方向一致的缺口。TinaCMS 的价值在于：作者在真实页面上点一段文字直接改，而不是在一个脱离上下文的表单里猜它会长什么样。

    v7-cms 已经有一半基础：preview.devServerURL 会把真实站点嵌进 iframe。缺的是 iframe 与编辑器之间的双向桥——页面上标出可编辑区域，点击回传字段路径，编辑器滚动并聚焦到对应控件。

    为什么它不与保真冲突：它只改字段值，不改文件结构。正文仍然走双轨判定，MDX 仍然只读源码。这和 Storyblok 那种拖拽重排布局是两回事。

    主要风险：被嵌页面需要暴露锚点信息（哪个 DOM 节点对应哪个字段路径），这要求主题侧配合。可行的做法是让预览注入一层脚本，按 frontmatter 键名给元素加标记，而不是要求主题改模板。

工程量参考

上面三条里，前两条合计约一天（含测试）。可视化内联编辑明显更大——需要预览注入层、字段路径映射、滚动定位、以及主题侧的可选配合，粗估是三到五倍于前两条之和。

它的收益也最大：那是"用起来像不像一个现代编辑器"的分界线。但前提是你确实要在浏览器里写文章；如果写作主要发生在本地 pnpm dev:cms，优先级可以往后放。

这份分析的依据

  • 已有能力来自源码与测试，不是文档：字段类型表在 fields-builtin.ts，双轨判定在 BodyField.tsx，保真测试是黄金文件。
  • "不做"的判断基于一个约束：v7-cms 的资产是"绝不改动未编辑的内容"。任何要求它理解并重写文件结构的功能，都在消耗这个资产。
  • 没有列出的不等于不做。这份清单只对照你给的四类，不代表完整路线图。
